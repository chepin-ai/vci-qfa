# LABJUDGE-EXT09 三草案判定

## 案① CIRC重做立项（主线B见证证书化内嵌A，C仅探针，AC1–AC5）

**路线稳健性：中高。**
把主线押在 B 的“见证证书化”上，并以 A 作为内嵌的证明骨架，路线本身是自洽的：B 提供可外部核验的见证，A 提供内部推导链，二者不是并列竞争，而是“外壳/内核”关系。C 降为探针是明智的，避免了三线并进导致验收面爆炸。

**机器可复核性：中。**
AC1–AC5 若要保持可机器复核，必须满足：
- 每条 AC 都绑定一个**可执行判定器**（脚本/谓词/阈值），而不是自然语言描述；
- 见证证书要有**固定 schema**（字段、序列化、哈希口径）；
- A 的内嵌点要有**稳定标识**，否则“内嵌”无法被机器确认。

**制度漏洞：**
- “C 仅探针”缺少**探针失效时的降级规则**——若 C 长期无信号，是否仍算立项成立？
- “见证证书化”没有规定**证书撤销/过期**机制，容易形成一次性通过后的永久豁免。
- AC1–AC5 未给出**优先级与豁免关系**，可能出现“五条都写、只过一条也宣布 pass”。

**结论：有条件通过（pass-with-conditions）。** 需补：证书 schema、AC 判定器清单、C 探针失效降级规则。

## 案② 缓存锚域限条款（fallthrough DONE 四条件 + BLOCKED 四触发 + 缓存锚≠内容认证）

**路线稳健性：高。**
把“缓存锚”与“内容认证”显式解耦，是这一案最关键的正确决策。缓存锚只能证明“某处曾出现过某引用”，不能证明“内容为真/为最终版”。DONE/BLOCKED 各四条件，形式上对称，利于机器判定。

**机器可复核性：高（前提是条件可判定）。**
- DONE 四条件必须是**合取**，且每条可被独立观测；
- BLOCKED 四触发必须是**析取**，任一触发即停；
- “缓存锚≠内容认证”应写成**类型级禁止**（例如 anchor 不得作为 auth 的入参），这样机器可静态检查。

**制度漏洞（重点）：**
1. **DONE/BLOCKED 边界重叠风险**：若某条件同时满足“可视为完成”和“可视为阻塞”，必须有**优先级规则**。建议：BLOCKED 优先于 DONE（安全侧优先），否则会出现“带病 DONE”。
2. **fallthrough 的默认方向未定**：四条件不满足时，是默认 BLOCKED 还是默认继续？必须显式规定，否则实现者会各自解释。
3. **缓存锚的“域限”缺少传递闭包规则**：锚 A 引用 B、B 引用 C 时，C 是否仍在域内？未规定则域限可被链式绕过。
4. **“≠内容认证”缺少反例测试要求**：应强制要求至少一个“锚存在但内容被篡改”的负例通过 BLOCKED，否则该条款是纸面条款。

**结论：通过，但需补边界优先级与传递闭包规则。** 这是三案中制度设计最扎实的一案。

## 案③ A1 堆叠升级（L0 确权锁边界，L1/L2 契约 JSON 化，DISPUTED 停层）

**路线稳健性：中。**
分层本身合理：L0 锁边界、L1/L2 契约化、DISPUTED 停层，符合“先定权、再定约、争议不扩散”的思路。风险在于**层间停让规则**如果只写“停层”而不写“停在哪一层、由谁裁决、何时恢复”，会变成事实上的死锁。

**机器可复核性：中高。**
- L1/L2 契约 JSON 化天然可机器复核，这是优点；
- L0 的“确权锁边界”需要**边界谓词**，否则“锁”是修辞；
- DISPUTED 停层需要**状态机**（进入、保持、退出三条件），否则无法机器判定。

**制度漏洞（重点）：**
1. **层级停让规则不完整**：DISPUTED 时是停 L1 还是停 L1+L2？L0 是否豁免？未规定则争议可被用来冻结整链，形成**否决权滥用**。
2. **升级路径缺少回滚**：L0→L1→L2 升级后若发现 L0 确权有误，是否有降级/回滚协议？无则错误会被固化。
3. **JSON 契约的版本兼容未定**：L1/L2 契约演化时，旧 JSON 是否仍可判？需要显式版本字段与兼容策略。
4. **DISPUTED 停层与案②的 BLOCKED 关系未定义**：两套“停”机制若并存，需规定谁优先，否则跨案组合时会出现双重停层或互相绕过。

**结论：有条件通过。** 需补：DISPUTED 状态机、L0 回滚协议、与案② BLOCKED 的优先级。
